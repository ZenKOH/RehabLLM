# v0.4.1 — reliable experiments before another GPU session

This update repairs the existing v0.4 workflow and starts the CPU retrieval layer. It does not retrain the 17.4M model or establish better rehabilitation answers.

## Changes and reasons

| Previous behaviour | v0.4.1 behaviour |
| --- | --- |
| SFT used `tokenizer.pad_id`, absent from the real wrapper | Padding ID is exposed and tested with a real SentencePiece model |
| Long instructions/contexts could consume almost the whole window and silently leave a fragment of the answer | The entire dataset is encoded and checked before checkpoint loading; overflow is rejected with an example identifier |
| Different responses to the same question could land in both splits | Normalised instruction/context groups stay in one split; training independently rejects overlap |
| SFT validation averaged batch losses equally and could repeat a short validation set | Loss is weighted by supervised response tokens; each selected validation batch is read once |
| Inference continued after EOS; evaluator decoded the prompt with the answer | EOS stops generation; reports contain completion-only text and an explicit stopping reason |
| Sampled evaluation varied with global training RNG state | A local fixed sampling seed leaves training RNG untouched |
| A long chat prompt could silently lose its beginning | The controlled inference path rejects overlong prompts and caps generation before the original prompt is lost |
| No matched experiment comparison | Reports hash checkpoint/tokenizer/test/questions; comparison rejects mismatched settings or inputs |
| CPU/GPU gate accepted internally inconsistent statistics | Category/split totals and cleaning character counts are checked |
| CLI corpus default differed from the notebook target | Both default to 4,500 selected documents |

The model architecture and tokenizer vocabulary remain unchanged. Old checkpoints can still be loaded. New instruction data must satisfy the stricter complete-answer contract.

## Run the corrected experiment

1. Open [RehabLLM_v04_Clean_Enrich_SFT.ipynb](../notebooks/RehabLLM_v04_Clean_Enrich_SFT.ipynb) in Colab/Kaggle and supply the existing v0.3 checkpoint/tokenizer locations.
2. Complete CPU corpus preparation. The notebook rebuilds only the cheap instruction split and audits it with the original tokenizer. Retrieval/cleaning/token caches are retained.
3. Inspect the corpus and instruction audit reports. A corpus HOLD or instruction overflow must be resolved before training.
4. Enable a GPU and run continued pretraining, then the seed-SFT smoke test. The revised seed run uses `v04_sft_seed_r1` so an older completed seed run cannot be mistaken for the revised run.
5. Run the matched evaluation cell. It tests v0.3, domain continuation and seed SFT using identical instruction-format prompts, sampling settings and held-out tokens. It packages the reports and comparisons with the checkpoints.
6. Review the paired outputs for relevance, factuality, uncertainty, source fidelity and safety. The bundled seed demonstrates mechanics; it is insufficient for a production instruction model.

To preflight a larger instruction corpus directly:

```bash
python scripts/prepare_instructions.py --input your_instructions.jsonl
python scripts/audit_instructions.py \
  --train data/v04/instructions/train.jsonl \
  --val data/v04/instructions/val.jsonl \
  --tokenizer /path/to/original/rehab_sp.model --context-length 512
```

Shorten or divide oversized examples while preserving support for their answers. The trainer does not silently discard evidence, questions or response tokens. Prompt grouping prevents exact normalised prompt/context leakage; it does not detect semantic paraphrases or shared source documents. Curators must group those independently.

## What has been validated

The automated suite includes a real SentencePiece tokenizer, prompt/response masking, complete-answer overflow rejection, EOS stopping across a batch, token-weighted validation, deterministic evaluation, a two-step CPU SFT run, checkpoint loading, matched CLI evaluation/comparison, and local evidence-index provenance/atomicity checks. CI runs on Python 3.10, 3.11 and 3.12 with CPU PyTorch.

These are software checks. Actual v0.4 corpus composition, full GPU training, held-out model quality and clinical reliability require separate experiment results. A lower language-model loss does not establish better clinical answers.

## Evidence retrieval

The [evidence index](EVIDENCE_RETRIEVAL.md) provides original passages and provenance without an external model. It is the first part of the planned v0.5 retrieval work. Generated cited answers, semantic citation verification, a representative retrieval benchmark and a deployed inference service are not included in this release.
