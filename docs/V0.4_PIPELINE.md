# RehabLLM v0.4 — corpus autopsy, cleaning, robotics enrichment and instruction tuning

## Why v0.4 exists

The first substantial v0.3 free-GPU run proved that the end-to-end training stack works, but it also exposed the model's dominant failure mode.

Observed v0.3 baseline:

- 17,437,440 parameters
- 3,546 accepted documents
- 16,852,786 training tokens
- 3,016 core rehabilitation documents
- 394 assistive-technology documents
- 104 neurotechnology documents
- 32 rehabilitation-robotics documents
- held-out test loss: 4.1881
- held-out perplexity: 65.90
- generated output continued scientific-paper boilerplate instead of directly answering the prompt

The representative failure began with competing-interest and author-contribution language, then moved into an Introduction section. That means v0.3 learned real biomedical-paper structure, but not yet useful assistant behaviour.

v0.4 attacks that mechanism directly.

## Pipeline

```text
v0.3 corpus / fresh source corpus
  ↓
corpus autopsy
  ↓
publishing-boilerplate + markup cleaning
  ↓
targeted PMC robotics / neurotechnology enrichment
  ↓
quality filtering + exact/near deduplication
  ↓
mixture selection
  ↓
tokenise with the EXISTING v0.3 SentencePiece tokenizer
  ↓
continue pretraining from v0.3 model weights with a fresh optimiser
  ↓
instruction-data validation and split
  ↓
supervised instruction tuning (prompt loss masked)
  ↓
instruction-style generation + held-out evaluation
```

## Critical tokenizer rule

Do **not** train a new tokenizer when continuing from the v0.3 checkpoint.

The v0.3 model learned token embeddings and an output matrix for its existing 8,000-token SentencePiece vocabulary. Replacing the tokenizer would change token identities while leaving the learned embedding rows in place.

v0.4 therefore reuses the v0.3 tokenizer for domain continuation and SFT.

## 1. Corpus autopsy

Audit JSONL or text-split corpora:

```bash
python scripts/autopsy_corpus.py \
  --input data/curated/articles.jsonl \
  --out-json reports/v04_corpus_autopsy.json \
  --out-md reports/v04_corpus_autopsy.md
```

The autopsy reports domain mix and configured contamination markers, including:

- competing interests / conflicts
- author-contribution sections
- acknowledgements
- funding
- data-availability statements
- ethics boilerplate
- references
- section anchors such as `{#sec1}`
- residual HTML tags

## 2. Targeted robotics enrichment

Use the PMC profile designed specifically for rehabilitation robotics:

```bash
export NCBI_EMAIL="your-contact-email"
python scripts/fetch_pmc.py \
  --profile robotics \
  --retmax-per-query 200 \
  --max-articles 1800 \
  --out data/raw/pmc_robotics_v04.jsonl
```

The query plan explicitly covers:

- stroke upper-limb robotics
- robotic gait training
- wearable exoskeletons
- hand/wrist robotics
- SCI exoskeletons
- motor-learning robotics
- BCI + robotics
- FES + robotics
- EMG / intent-driven robotics
- safety, usability and implementation

The existing PMC safeguards remain: discovery through NCBI E-Utilities, article-level rights verification through PMC OAI-PMH, BioC full text, permissive licence allow-list, and integrity filters for retractions / expressions of concern.

## 3. Build the v0.4 domain corpus

Combine the broad source corpus and targeted enrichment:

```bash
python scripts/build_v04_corpus.py \
  --input data/curated/articles.jsonl data/raw/pmc_robotics_v04.jsonl \
  --out-dir data/v04 \
  --target-docs 4500
```

The default notebook aims for roughly 4,500 selected documents. The target mixture is:

- 45% core rehabilitation
- 30% rehabilitation robotics
- 15% neurotechnology
- 10% assistive technology

These are targets, not a licence to duplicate scarce papers. The builder never fills a category target by copying the same document. It reports shortfalls explicitly.

## 4. Tokenise with the existing v0.3 tokenizer

```bash
python scripts/prepare_data.py \
  --train-text data/v04/train.txt \
  --val-text data/v04/val.txt \
  --test-text data/v04/test.txt \
  --tokenizer /path/to/v03/rehab_sp.model \
  --out-dir data/v04/processed
```

## 5. Continue pretraining from v0.3 weights

v0.4 adds `--init-checkpoint`.

Unlike `--resume`, this loads **model weights only** and starts a fresh optimiser and learning-rate schedule for the new corpus.

```bash
python scripts/train_model.py \
  --config configs/v04_domain.yaml \
  --train data/v04/processed/train.bin \
  --val data/v04/processed/val.bin \
  --out checkpoints/v04_domain \
  --init-checkpoint /path/to/v03/final.pt
```

The default continuation schedule uses a lower peak learning rate than the original pretraining run.

## 6. Instruction data

Instruction JSONL schema:

```json
{"id":"example-id","instruction":"Question or task","context":"Optional evidence/context","response":"Desired answer"}
```

The repository includes `data/instruction_seed.jsonl` only as a **format and SFT smoke-test set**. It is intentionally small and must not be treated as sufficient instruction data for a useful assistant.

Prepare it:

```bash
python scripts/prepare_instructions.py \
  --input data/instruction_seed.jsonl \
  --out-dir data/v04/instructions
```

For a meaningful v0.4 assistant experiment, grow the human-reviewed instruction set substantially before using the full `configs/v04_sft.yaml` schedule. The seed config `configs/v04_sft_seed.yaml` is intentionally short to avoid extreme overfitting on the included examples.

## 7. Supervised instruction tuning

Seed smoke test:

```bash
python scripts/train_sft.py \
  --config configs/v04_sft_seed.yaml \
  --base-checkpoint checkpoints/v04_domain/final.pt \
  --tokenizer /path/to/v03/rehab_sp.model \
  --train data/v04/instructions/train.jsonl \
  --val data/v04/instructions/val.jsonl \
  --out checkpoints/v04_sft_seed
```

The SFT dataset masks prompt tokens with `-100`, so causal-language-model loss is calculated on the answer tokens rather than teaching the model to reproduce the instruction.

## 8. Test direct-answer behaviour

```bash
python scripts/chat_sft.py \
  --checkpoint checkpoints/v04_sft_seed/final.pt \
  --tokenizer /path/to/v03/rehab_sp.model \
  --instruction "Explain robot-assisted rehabilitation after stroke, including important evidence limitations."
```

The first behavioural gate is simple: the answer should respond to the instruction rather than continue into author contributions, competing interests, section metadata or a generic paper Introduction.

## v0.4 quality gates

A v0.4 run should be reviewed against all of these, not perplexity alone:

1. **Contamination:** configured boilerplate markers fall materially after cleaning.
2. **Mixture:** robotics / neurotechnology representation improves transparently without duplicate oversampling.
3. **Language modelling:** held-out loss remains stable enough to show the model has not catastrophically forgotten basic domain language.
4. **Instruction following:** generated text answers the task directly.
5. **Uncertainty:** the model does not convert mixed evidence into categorical clinical claims.
6. **Safety:** no patient-specific treatment prescription, stimulation parameter selection or autonomous device-control advice.
7. **Provenance:** source and licence fields remain traceable wherever the underlying corpus provides them.

## What v0.4 still will not solve

At 17.4M parameters, even a cleaner and instruction-tuned RehabLLM remains a small research model. v0.4 is intended to test whether better data and post-training materially improve behaviour before spending compute on a 50–100M parameter successor.

The next scaling decision should be evidence-driven: compare v0.3 and v0.4 on held-out loss, corpus contamination, direct-answer behaviour and human-reviewed rehabilitation prompts before increasing model size.


## GPU readiness gate

Before another free-GPU run, assess the prepared corpus:

```bash
python scripts/assess_v04_readiness.py \
  --stats data/v04/v04_corpus_stats.json \
  --out reports/v04_readiness.json
```

The default gate requires:

- at least 3,500 selected documents;
- at least 12% rehabilitation robotics;
- at least 5% neurotechnology;
- at least 20% robotics + neurotechnology combined;
- at least 100 validation and 100 test documents;
- cleaning statistics to be present and no more than 30% of source characters removed.

These are **minimum experiment-readiness thresholds**, not quality claims. The aspirational mixture remains 30% robotics and 15% neurotechnology. A HOLD result means improve the corpus before spending GPU time.
